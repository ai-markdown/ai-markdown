# Performance Lab

Use these instruments to compare rendering paths on your own workload. The

<a href={DOCS_LINKS.benchmark}>benchmark guide</a> records a July 2026 study on 1.x development builds; its numbers are
historical measurements, not expected results for the current version or a different machine.

## What is being measured

- **Block memoization** (`blockMemo`) lets React reuse unchanged rendered block
  plans and skip their HAST-to-JSX conversion. Child state and context updates
  still work. Standalone output should remain equivalent; coordinated references
  require this path to stay enabled.
- **Incremental parsing** (`incrementalParse`) retains a verified prefix and
  parses the remaining tail when the source and configuration permit it. An
  append alone does not guarantee reuse. React requires `blockMemo` for this path.

Same-page comparison stories check the two rendered outputs as frames arrive,
normalizing generated document prefixes. A clean run establishes agreement for
that run's inputs and configuration. It does not prove equivalence for every
possible document. Cross-chunk comparisons keep block memoization enabled on both
sides and vary incremental parsing.

## Run a comparison

Choose a scenario and payload, then use the story's run or restart control.
Where available, `content` accepts your own Markdown. Readouts include React
commit counts and durations, selected pipeline timings, frame gaps and long tasks.
The available measurements differ by instrument.

Compare several runs with the same settings. Background tabs, extensions, thermal
state and other work can change results. Small payloads or one unfinished block
may offer little reusable work. Same-page comparisons share a main thread, so
frame-rate and long-task measurements cannot be attributed independently to each
side. Development-mode React timings are not production latency estimates.

## Isolated comparisons

`BlockMemoCompareIsolated`, `IncrementalParseCompareIsolated` and
`BoostCompareIsolated` load the sides from `localhost` and `127.0.0.1`. Both origins
must serve the same catalog. These stories require a local dev server or static
build reachable through both hostnames; other deployments show a readiness message.

The separate sites allow Chromium's site isolation to separate renderer work;
process assignment still depends on the browser and its configuration. Record that
environment when interpreting per-side measurements. These stories are excluded
from the automated story suite because they require the paired-origin setup.

The isolated stories report timings without the same-page DOM comparison. Use the
same-page comparisons to check output agreement as well.

## Verification boundaries

The dense performance panels disable automated accessibility assertions. Passing
the browser suite therefore does not establish their accessibility conformance.
Engine equivalence tests, release soak, adapter lifecycle tests and production
browser benchmarks have separate scopes.
